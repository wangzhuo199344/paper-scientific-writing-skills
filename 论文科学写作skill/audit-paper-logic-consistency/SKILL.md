# 全文逻辑与一致性审查

## 通用约束

- 以用户提供的当前稿件、数据、文献和投稿要求为依据。先读取相关内容，不用记忆中的旧版本替代当前材料。
- 默认中文学术表达，使用具体、精炼、连贯的段落；用户指定语言、长度、格式和范围时优先遵守。
- 不编造数值、文献、对比优势、因果关系或创新性。区分已有证据、作者解释与待验证设想；证据不足时明确标为待核实。
- 先完成现有材料能支持的工作；只有缺失信息会影响核心结论时才提出必要问题。不得把用户未回答的内容当作事实。
- 用户只要求文字时直接输出文字；要求修改文件时使用当前环境适用的文档技能，保留原格式并验证交付文件。
- 不强行套用固定论文模板。实证、理论、算法及定性研究均可使用，以研究自身的证据类型和学科规范为准。

## 工作流程

1. 阅读用户提供的当前稿件和补充材料，建立章节覆盖清单。材料不完整时说明已审范围；未提供的章节标为无法判断，不当作内容缺失。
2. 提取Problem → Gap → Idea → Method → Claim → Evidence链条。将每个缺口、设计、主张和证据关联到具体章节段落或图表。
3. 按四种一致性检查：问题一致性（Title、Abstract、Introduction）；方法一致性（Introduction动机与Method实现）；主张一致性（Abstract、Contributions、Conclusion）；证据一致性（Experiments或其他论证是否真正支持Claim）。
4. 检查前文建立的预期是否在后文兑现，后文证据是否有前文动机。额外探索性分析可以保留，但必须明确性质，不机械判为错误。
5. 检查数字、单位、样本、对象、术语、条件及结论强度的跨章节冲突，特别关注摘要与正文以及中英文对应。不自动裁决无法确认的数值，以原始数据或明确权威版本为准。
6. 先排序研究逻辑问题，再排序论证结构问题，最后语言表达问题。区分确定性错误、需要作者核实的问题和可选优化，不把写作偏好当作事实错误。
7. 用户授权修改时直接修正能确定的内容；证据缺失、数据冲突及实验不足只标注并建议验证，不捏造结果。

## 默认输出

先给出有范围限定的审查判断，再给出按优先级排列的清单：位置／问题与依据／影响／具体修改建议／是否待核实。必要时附“Gap／Method或Design／Claim／Evidence／状态”矩阵。缺少证据不等于方法一定无效。

## 交付检查

每项问题是否有可定位依据？是否把已证实问题和推测混为一谈？是否优先解决前两个层次而非只润色？是否错误宣称复算或核实了未检查的材料？
