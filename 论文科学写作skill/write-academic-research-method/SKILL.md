# 研究方法与公式阐释

## 执行约束

- 先读取用户提供的当前稿件、文献、数据和目标要求；只检查已提供的部分，不将未提供材料判定为论文缺失。
- 默认使用精炼、连贯的中文学术表达；遵守用户指定的语言、长度、范围和格式。只要求正文时只输出正文。
- 不编造文献、数据、实验结果、创新性或统计显著性；区分观测、解释、已验证结论和待验证假设。证据不足时标为待核实。
- 将课件原则转为任务流程，按研究类型调整，不把算法实验模板强加给理论、实证或定性论文。
- 先完成现有材料能支持的工作。要求修改 Word 等文件时使用环境适用的文档工具，保留格式并验证；本技能自身不包含文件渲染工具。

## 按需参考

执行本技能时读取 [references/source-guidance.md](references/source-guidance.md)，其中记录原文规则、模板和使用边界。

## 工作流程

1. 提取已实现的方法、代码或技术说明，定义问题、输入、输出、目标、假设和约束。未知实现与建议设计明确分开，不把建议写成已完成的方法。
2. 按“问题定义 → 整体框架 → 关键设计 → 算法与公式 → 实现细节”建立章节顺序，可依据论文类型合并调整。
3. 总体框架先提供理解地图，说明输入、信息流、主要模块及输出之间的关系。图中连线应对应真实依赖，区分训练、校准与推理；没有实际模块关系时先输出待确认草案。
4. 对每项核心设计写出“Challenge → Required Capability → Design”：解决哪个问题，需要什么能力，采用何种思想，如何实现，与已有方式的关键差异在哪里。避免“先用A，再加B，最后用C”的模块流水账。
5. 在公式前说明定义或推导目的，在公式后解释主要符号、含义、单位、维度和适用假设。同一符号不要在不同位置表示不同含义；关键式需理论、定义或文献依据。省略推导时仍保留理解和复现所需的信息。
6. 让文字解释目的与直觉，数学定义保障准确，算法或流程说明执行顺序；三者互补，不逐字重复同一计算。未提供的推导不声称已经证明。
7. 核对训练、推理、参数、初始化、停止条件及环境信息是否足以复现实际研究；仅要求与方法相关的项目。不擅自填入学习率、模型规模、硬件或复杂度。
8. 检查引言中的设计动机、方法章节、框架图、模块名和消融项一致。对没有验证的机制解释标明待验证。

## 默认交付

交付方法正文；审查时列出“问题或挑战／所需能力／设计／公式或实现位置／验证依据”，并给符号冲突与待补实现清单。框架草图不代替实现证据。

## 完成检查

读者是否能解释每项设计为什么存在、如何运行和如何验证？公式、文字、算法和框架图是否相互一致？是否将建议写成已实现事实？
